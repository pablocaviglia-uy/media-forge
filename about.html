Convertí video y audio sin subirlo a ningún lado. Convert video and audio without uploading it anywhere.

Convertir un video suele significar subirlo al sitio de un desconocido, esperar, y bajar el resultado. Acá todo pasa en la pestaña: el archivo no se sube, y no hay servidor al que subirlo. Es FFmpeg, el de siempre, compilado a WebAssembly y corriendo en tu propio procesador. Converting a video usually means uploading it to a stranger's website, waiting, and downloading the result. Here everything happens in the tab: the file is never uploaded, and there is no server to upload it to. It is FFmpeg — the same FFmpeg — compiled to WebAssembly and running on your own processor.

Por qué Why

Para casi todo el mundo, convertir un video sigue siendo abrir el primer conversor online que aparece, arrastrar el archivo y esperar. Ese archivo muchas veces es de un cliente, o una reunión grabada, o los hijos de alguien. Nadie decidió mandarlo a un servidor ajeno; simplemente era el camino de menor fricción. For most people, converting a video still means opening the first online converter that comes up, dragging the file in and waiting. That file is often a client's, or a recorded meeting, or somebody's children. Nobody decided to send it to a stranger's server; it was just the path of least friction.

FFmpeg hace exactamente esto en tu propia máquina desde hace veinte años. Lo que falta no es la herramienta: es instalarla, mantenerla, y acordarse de los flags cada vez. FFmpeg has done exactly this on your own machine for twenty years. What is missing is not the tool: it is installing it, keeping it, and remembering the flags every time.

Esto es el mismo camino de menor fricción, sin la parte de subir el archivo. This is that same path, without the upload.

Hace las dos pasadasDoes the two passes

Un GIF decente necesita construir una paleta a partir del clip y recién después cuantizar contra ella. Apuntar a un tamaño de archivo necesita medir antes de comprometerse a un bitrate. Las dos cosas son dos corridas de FFmpeg, y las hace. A decent GIF needs a palette built from the clip before anything is quantised against it. Hitting a target file size needs a measuring pass before committing to a bitrate. Both are two runs of FFmpeg, and both are done properly.

El motor es FFmpeg 5.1.4 compilado a WebAssembly (@ffmpeg/core 0.12.10). No viene de un CDN: está vendorizado en el repositorio, en assets/ffmpeg/, 32 MB, con el SHA-256 de cada archivo anotado en manifest.json para que cualquiera pueda comprobar que los bytes son los publicados. Corre dentro de un Worker, porque exec bloquea su hilo del primer argumento al último cuadro: en el hilo principal la página se congelaría, sin barra de progreso, hasta que el trabajo terminara. The engine is FFmpeg 5.1.4 compiled to WebAssembly (@ffmpeg/core 0.12.10). It does not come from a CDN: it is vendored in the repository, at assets/ffmpeg/, 32 MB of it, with the SHA-256 of every file recorded in manifest.json so anyone can verify the bytes are the published ones. It runs inside a Worker, because exec blocks its thread from the first argument to the last frame: on the main thread the page would freeze, with no progress bar, for as long as the job took.

Corre en un solo hilo, y no es un descuido. La build multihilo necesita SharedArrayBuffer, que necesita que la página esté aislada entre orígenes, que necesita dos cabeceras de respuesta HTTP que GitHub Pages no puede mandar. La build multihilo es, además, apenas unas dos veces más rápida, y dentro de un WebView de Android directamente no existe. Si lo hospedás detrás de un servidor que sí puede mandar esas cabeceras, la app se da cuenta sola y levanta el core rápido. It runs single-threaded, and that is not an oversight. The multi-threaded build needs SharedArrayBuffer, which needs the page to be cross-origin isolated, which needs two HTTP response headers GitHub Pages cannot send. The multi-threaded build is also only about twice as fast, and inside an Android WebView it does not exist at all. If you self-host this behind a server that can send those headers, the app notices and picks the faster core up on its own.

Lo que no puede hacer What it cannot do

Es lento. Unas 25 veces más lento que el mismo trabajo con un ffmpeg nativo, según el benchmark publicado de este proyecto. Es una máquina virtual dentro de una pestaña, en un solo núcleo. Para clips cortos no importa; para una película, buscá otra cosa. It is slow. Roughly 25 times slower than the same job with a native ffmpeg, by this project's own published benchmark. It is a virtual machine inside a browser tab, running on one core. For short clips that does not matter; for a feature film, use something else.

Hay un techo de tamaño, y es duro. El heap de WebAssembly es de 32 bits y tope 2 GB, y la entrada, la salida y los buffers de trabajo del códec viven ahí adentro al mismo tiempo. La app rechaza archivos de más de 500 MB y avisa a partir de 150 MB. Decirlo antes de empezar es mejor que morirse a mitad de camino con un error de asignación de memoria. There is a hard ceiling on size. The WebAssembly heap is 32-bit and capped at 2 GB, and the input, the output and the codec's working buffers all live in it at once. The app refuses files over 500 MB and warns above 150 MB. Saying so before starting is better than dying halfway through with a memory allocation error.

El WebM que produce es VP8, no VP9. libvpx-vp9 está compilado en el core y aparece en -encoders, pero en un core recién instanciado revienta con «memory access out of bounds» antes del primer cuadro. No está simplemente roto: después de unas cuarenta invocaciones sobre la misma instancia empieza a andar, que es peor — el motor arranca de cero en cada carga de la página, así que una primera conversión real siempre cae en el rango donde se lleva puesta la instancia entera. The WebM it produces is VP8, not VP9. libvpx-vp9 is compiled into the core and shows up in -encoders, but on a freshly instantiated core it traps with "memory access out of bounds" before the first frame. It is not simply broken: after roughly forty invocations on the same instance it starts working, which is worse — the engine is new on every page load, so a real first conversion always lands in the range where it takes the instance down.
